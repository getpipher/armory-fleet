### What 6-3 closes

- **Workflows-as-code (PRD §8: "JS orchestration with `agent`/`parallel`/`pipeline`/`phase` + journaled resume / edit-and-resume"):** today orchestration is a *single* `subagent` delegate or a *fixed* superpowers lifecycle (brainstorm→plan→implement→review→finish). There is no surface for the model (or a human) to author an arbitrary JS script that fans work out across N agents, routes each to a tier, cross-checks results, and resumes deterministically after interruption. 6-3 adds that surface: a `vm`-sandboxed JS-DSL realm where `agent()`/`parallel()`/`pipeline()`/`phase()`/`workflow()` compose, a `WorkflowJournal` keys results by positional call index for replay/edit-and-resume, and 7 quality helpers (`verify`/`judgePanel`/`loopUntilDry`/`completenessCheck`/`gate`/`retry`/`checkpoint`) live as a **separate layer** from 6-2's phase-exit gates.
- **The 6-2.1 deferral (CLOSED):** `judgePanel` and `loopUntilDry` were deferred from 6-2 ("build once the gate seam is proven"). 6-3 ships them — not as phase-exit gates (wrong layer — they're *looping* primitives, not per-phase-exit checks) but as workflow helpers in `src/workflows/helpers/`. Same names, different layer, documented.
- **The v0.11.1 `isolation` seam (INHERITED, not re-plumbed):** the v0.11.1 patch split `runBackground` into `runBackgroundInPlace` (git-agnostic core) + `runBackgroundIsolated` (worktree wrapper, sync pre-flight) + `runBackgroundAuto` (router). 6-3's `agent(prompt, { isolation: "worktree" })` calls `runBackgroundIsolated`; default `agent()` calls `runBackgroundInPlace`. No new isolation plumbing — reuse the shipped fns.

### What 6-3 defers (YAGNI)

- **A bespoke schema-repair loop:** `agent({ schema })` validates + re-spawns via the existing `retries` count (one repair attempt per retry). No dedicated "fix the JSON" loop — `retries` covers it; a repair loop is gold-plating until users hit it.
- **Phase-level `budget`:** run-level + agent-level `budget` ship; per-phase budgets defer (the `phase(title, { budget })` option accepts but ignores it — documented).
- **`pi.registerWorkflowHelper` extension hook:** YAGNI. The 7 helpers are a fixed layer; users compose them in JS. If a real need emerges, the registry pattern (mirroring `GateRegistry`) is the path — but not this SPEC.
- **Persisted agent sessions for workflow children:** children stay in-memory by default (matching the v0.11.1 posture). `persistAgentSessions` is a post-v1 concern.

### The moat extension

Per PRD §3, workflows-as-code is **table-stakes parity** (QuintinShaw owns it, 287⭐). 6-3 reaches parity on the orchestration surface *and* extends the moat: a workflow `agent()` call can opt into `{ lifecycle: "default" }` — running a full superpowers lifecycle (with 6-2's gate chain) as one workflow step. No competitor offers lifecycle-as-a-workflow-step; it's the composition the moat is built on.

### 3.1 The `vm` realm (determinism, not security)

A workflow script runs in a Node `vm.createContext()`. Per Q5=A and QuintinShaw's exact model: **the realm is for determinism, not a security boundary** (PRD §6 non-goal: "trusted-dev-environment, same posture as every peer"). What's stripped vs. injected:

| Stripped (non-deterministic / unsafe) | Injected (deterministic / fleet-owned) |
|---|---|
| `Date.now`, `Math.random`, `new Date` | `log(message)` — appends to the workflow's progress (visible in the Workflows view) |
| `require`, `import` (no module access) | `args` — the run's input (from `workflow({ args })`); `unknown` |
| filesystem (`fs`), network (`net`/`http`) | `cwd` — string (the session cwd); `process.cwd()` returns it |
| `setTimeout`/`setInterval` (no timers) | `budget` — `{ total, spent(), remaining() }` (run-level token budget; Q6=A) |
| `eval`, `Function` (no eval) | the 5 orchestration globals + 7 helpers (below) |
| `globalThis`, `process.env` (no leak) | `phase(title, opts?)` — sets the current phase for the live view + `agent()` label derivation |

The realm is **JS-only** (Q5=A): workflow scripts are `.js`, never `.ts`. The extension source stays `.ts` (raw via tsx, no build step — getpipher convention); only the *user-authored/generated* scripts are JS. This means no transpile step in the hot path and no build dependency for the workflow surface.

**Why `vm` and not just a closure:** `vm.createContext` gives us a clean globals surface to inject + strip. A closure would leak `Date`/`Math.random`/`require` via the lexical scope — the whole point of the determinism contract (journal replay reliability) is that those are absent. `vm` lets us build an explicit allowlist. It is *not* a sandbox against a hostile script (PRD §6: trusted-dev-environment); a determined script can escape `vm` via `Symbol`/proxy tricks. We accept that — same posture as QuintinShaw and every peer.

### 3.2 The 5 orchestration globals

All async; all journaled by positional call index.

#### `agent(prompt, options?) => Promise<string | structured value | null>`

The atomic unit. Spawns one subagent (a normal `RunRecord` + `RunLog` entry linked to the workflow `runId`), awaits its result, journals it by call index.

| Option | Type | Default | Maps to |
|---|---|---|---|
| `label` | string | derived from phase + call count | `RunRecord` display label |
| `phase` | string | current phase (from `phase()`) | `RunRecord` phase tag |
| `schema` | plain JSON Schema | none | post-spawn validation; on mismatch, re-spawn (counts against `retries`) |
| `model` | `provider/modelId` or `provider/modelId:thinking` | agent's resolved model | `spawnSubagent` `model` override |
| `tier` | string | agent's tier | 6-1 `TierRegistry.get(tier)` → `resolveAgentModel` |
| `isolation` | `"worktree"` | in-place (no worktree) | v0.11.1 seam: `"worktree"` → `runBackgroundIsolated` (sync pre-flight); default → `runBackgroundInPlace` (the core, no worktree). Workflow `agent()` does **not** use `runBackgroundAuto` — it defaults to in-place (matches QuintinShaw's opt-in-`worktree` model), unlike the `subagent` tool's `auto` default (worktree-in-git). The runner reuses the *functions*; it picks a different default routing. |
| `agentType` | string | `"general-purpose"` | the agent registry (frontmatter `AgentDef`) |
| `timeoutMs` | number \| null | run timeout | per-agent timeout (null = unbounded) |
| `retries` | number | run retry count | recoverable-failure re-spawns (also covers schema-mismatch repair) |
| `lifecycle` | string | none | **the moat (Q1=C):** run a full superpowers lifecycle as this one `agent()` step — calls `runLifecycle(name)` with the prompt as the task; the lifecycle's phase-exit gates (6-2) run inside |

**The `lifecycle` bridge (Q1=C — the moat composition):** `agent("audit the routes", { lifecycle: "default" })` doesn't spawn one agent — it runs the whole brainstorm→plan→implement→review→finish pipeline as a single workflow step, returning the lifecycle's final synthesized result. The 6-2 gate chain runs *inside* each phase of that lifecycle. No competitor offers this — a workflow step that is itself a gated multi-phase pipeline. This is the uncopyable composition.

**Isolation reuse (v0.11.1 seam):** `agent(prompt, { isolation: "worktree" })` calls `runBackgroundIsolated` (the wrapper: `WorktreeService.isGitRepo()` sync pre-flight → fail-fast `{status:"failed",error}` if not a git repo → worktree create → run). Default `agent()` calls `runBackgroundInPlace` (the git-agnostic core — no worktree, no git dependency). The v0.11.1 split means **no new isolation plumbing**; 6-3 reuses the shipped functions directly. Note the deliberate default divergence: the `subagent` tool defaults to `auto` (worktree-in-git, because its background runs are typically *editing* runs that benefit from isolation); workflow `agent()` defaults to in-place (matches QuintinShaw's opt-in-`worktree` model, because workflow `agent()` calls are awaited single-shots where the author opts into worktree explicitly for parallel-edit safety). The runner reuses the *functions*; it picks a different default routing. (Workflow `agent()` calls are awaited — not fire-and-forget background runs; the reuse is the *isolation* logic, not the *background* pool. The runner holds the await; isolation is the orthogonal concern the v0.11.1 split already separated.)

#### `parallel(thunks) => Promise<Array<unknown | null>>`

Run an array of `() => agent(...)` thunks concurrently, preserve input order in the result array. Concurrency clamped to the run's `concurrency` setting (default 3, max 16 — matches QuintinShaw). Each thunk's `agent()` call is a separate positional journal entry (the call index is assigned at *execution* time, not declaration time — so the order in the journal reflects actual execution order, which is what makes replay deterministic).

#### `pipeline(items, ...stages) => Promise<Array<unknown | null>>`

Fan `items` through sequential stages: each stage is a `(item) => agent(...)` (or `(items) => agent(...)` batch) fn; the output of stage N feeds stage N+1. Order-preserving. Each `agent()` call inside a stage is journaled by execution index.

#### `phase(title, options?) => void`

Sets the current phase (for the live Workflows view + `agent()` label derivation). Optional `budget` (Q6=A deferral: accepted, ignored at phase level — documented). Not a checkpoint — purely a display + grouping primitive. Re-declaring `phase()` mid-script advances the current phase.

#### `workflow(savedName, childArgs?) => Promise<unknown>`

Run a saved workflow inline as a child of the current workflow. The child gets its own `runId` (linked to the parent via the journal) but shares the parent's `budget` pool (a child can't exceed the parent's run-level cap). Saved/user shadows builtin of the same name (Q2=C). Resolves to the child's return value.

### 3.3 The 7 quality helpers (separate layer from 6-2 — Q4=A)

Live in `src/workflows/helpers/`. **Same names as some 6-2 gates, different layer, different signatures** — this is the documented contract:

| Helper | 6-3 (workflow layer) signature | 6-2 (phase-exit gate) — for contrast |
|---|---|---|
| `verify` | `verify(item, opts?) => Promise<{real, realCount, total, votes}>` | `GateDef { run(ctx: GateCtx) }` — phase-exit, registry-resolved |
| `judgePanel` | `judgePanel(attempts, opts?) => Promise<{index, attempt, score, judgments} \| undefined>` | (was deferred — ships here) |
| `loopUntilDry` | `loopUntilDry({ round, key?, consecutiveEmpty?, maxRounds? }) => Promise<unknown[]>` | (was deferred — ships here) |
| `completenessCheck` | `completenessCheck(taskArgs, results) => Promise<{complete, missing?} \| null>` | 6-2 `completenessCheck` gate asserts phase artifacts exist |
| `gate` | `gate(thunk, validator, opts?) => Promise<{ok, value, attempts}>` | 6-2 `gate` gate asserts cost/context caps (predicate) |
| `retry` | `retry(thunk, opts?) => Promise<unknown>` | (no 6-2 equivalent) |
| `checkpoint` | `checkpoint(prompt, opts?) => Promise<unknown>` — **script-level human gate, standalone (not `CheckpointFn` reuse)** | 6-2 `CheckpointFn` is the lifecycle phase-exit decision fn |

The distinction is structural, not cosmetic: 6-2 gates are *phase-exit* (run after a phase's output, assert against `GateCtx` with `phaseRec`/`spawnRes`/`lifecycleCost`), resolved from a `GateRegistry` by name. 6-3 helpers are *call-site* (invoked inside a workflow script with arbitrary `item`/`attempts`/`results` arguments), imported as functions. The 6-2 `verify` spawns a reviewer against a *phase's* output; the 6-3 `verify` runs N reviewers against an *arbitrary item*. Same name, different scope — documented in code comments + this spec.

**`verify(item, { reviewers?, threshold?, lens? })`** — spawns `reviewers` (default 2) independent reviewer agents, each votes `{real: boolean, reason?}`; returns `{real, realCount, total, votes}`. `real = realCount/total >= threshold` (default 0.5). `lens` optionally scopes each reviewer's prompt.

**`judgePanel(attempts, { judges?, rubric? })`** — spawns `judges` (default 3) agents that each score every `attempt` against `rubric` (default "overall quality and correctness"); returns the highest-scoring `{index, attempt, score, judgments}`. Closes the 6-2.1 deferral — this is a *selection* primitive (pick the best of N), not a phase-exit pass/fail.

**`loopUntilDry({ round, key?, consecutiveEmpty?, maxRounds? })`** — calls `round(roundIndex)` to get `unknown[]`; de-dupes by `key` (default `JSON.stringify`); stops after `consecutiveEmpty` (default 2) empty rounds or `maxRounds` (default 50). Closes the 6-2.1 deferral — a *discovery* loop, not a phase check.

**`completenessCheck(taskArgs, results)`** — spawns one agent that judges whether `results` fully satisfy `taskArgs`; returns `{complete, missing?}` or `null` (agent couldn't judge). Workflow-layer: asserts against arbitrary results, not phase artifacts.

**`gate(thunk, validator, { attempts? })`** — runs `thunk(feedback, attempt)`; validates with `validator(value) => {ok, feedback?}`; on fail, re-runs `thunk` with the feedback (up to `attempts`, default 3). Returns `{ok, value, attempts}`. A generic retry-with-validation loop.

**`retry(thunk, { attempts?, until? })`** — runs `thunk(attempt)` up to `attempts` (default 3); `until(result)` (default: accept first) decides when to stop. Simpler than `gate` (no feedback loop) — for recoverable-failure retries.

**`checkpoint(prompt, opts?)`** — **the script-level human gate (Q4=A — standalone, not `CheckpointFn` reuse).** Pauses the workflow, surfaces `prompt` to the human via the Workflows view, awaits a response. `opts.kind` ("confirm"/"input"/"select", default "confirm"), `opts.choices`, `opts.default`, `opts.headless` ("default"/"abort" — what to do with no UI), `opts.timeoutMs`. In headless (model-driven) mode, `headless:"default"` returns `opts.default` (default `true`); `headless:"abort"` aborts the workflow. The response is journaled (by call index) so resume doesn't re-prompt. This is distinct from 6-2's `CheckpointFn` (which is the lifecycle's per-phase exit decision) — `checkpoint` is an inline script primitive the author places anywhere.

### 3.4 The `WorkflowJournal` (Q3=A)

New, separate from `RunLog`:

| Journal | Path | Granularity | Keying | Purpose |
|---|---|---|---|---|
| `RunJournal` (SPEC-5a) | `.pi/fleet/runs/<runId>.jsonl` | per-lifecycle-run | event log | the phase timeline + resume source for lifecycles |
| `RunLog` (SPEC-5b-1) | `.pi/fleet/conversations/<runId>.jsonl` | per-agent | event log | the conversation replay + Runs tab |
| **`WorkflowJournal` (this SPEC)** | `.pi/fleet/workflows/<runId>.jsonl` | per-workflow-run | **positional call index** | the agent-call cache for replay/edit-and-resume |

`WorkflowJournal` events:

```ts
interface WorkflowStartedEvent { type: "wf:started"; runId: string; script: string; args?: unknown; phases?: {title:string}[]; ts: number; }
interface AgentCallEvent { type: "agent:call"; callIndex: number; label: string; phase: string; prompt: string; opts: Record<string,unknown>; childRunId?: string; ts: number; }
interface AgentResultEvent { type: "agent:result"; callIndex: number; childRunId: string; result: unknown; status: "completed"|"failed"; costTotal?: number; tokenTotal?: number; ts: number; }
interface HelperCallEvent { type: "helper:call"; callIndex: number; name: string; args: unknown; ts: number; }
interface HelperResultEvent { type: "helper:result"; callIndex: number; name: string; result: unknown; ts: number; }
interface CheckpointEvent { type: "checkpoint"; callIndex: number; prompt: string; response: unknown; ts: number; }
interface WorkflowCompletedEvent { type: "wf:completed"; runId: string; result: unknown; costTotal?: number; tokenTotal?: number; ts: number; }
interface WorkflowAbortedEvent { type: "wf:aborted"; runId: string; reason: string; ts: number; }
```

**Positional call index (the determinism contract):** every `agent()` / helper / `checkpoint` call is assigned a monotonically-increasing `callIndex` at *execution* time. On resume (`resumeFromRunId`), the runner replays cached `agent:result` for call indices whose `prompt` + `opts` match the edited script's call at the same index; re-runs any that mismatch (edited) and everything after. This is QuintinShaw-exact (and Claude-Code-dynamic-workflows-exact): editing an `agent()` prompt in place reuses the cache up to that call and re-runs it + everything after. Inserting/removing/reordering an `agent()` call before others shifts their indices and invalidates the cache from that point on (mismatched calls simply re-run — no crash).

**Each `agent()` call is a normal `RunRecord` + `RunLog` entry linked to the workflow `runId`** (Q3=A). The child agent's `runId` is its own (`fl-…`); the `AgentCallEvent.childRunId` links them. So child agents appear in `/fleet` Fleet view + Runs view like any subagent — 6-2's cross-cwd filter + liveness probe + cost roll-up apply for free. The `WorkflowJournal` is the *workflow-level* resume cache; the `RunLog` is the *agent-level* conversation. Two concerns, two journals.

### 3.5 The runner (`src/workflows/runner.ts`)

```
runWorkflow(script, { args, runId, deps, mode, resumeFromRunId?, budget? }): Promise<WorkflowRunResult>

  1. genRunId (or reuse resumeFromRunId)
  2. load WorkflowJournal (resume: replay cached agent:results into a callIndex→result map)
  3. build the vm realm (vm-realm.ts): inject globals + helpers, strip non-determinism
  4. compile the script (vm.compileScript / new vm.Script) — JS only
  5. wf:started journal event
  6. execute the script in the realm:
     - each agent() / helper / checkpoint call → journal event + (for agent) spawn child via spawnSubagent
     - resume: for an agent() call whose callIndex has a cached result AND the prompt+opts match → return cached, no spawn
     - mismatch → spawn (re-run), overwrite the cache entry
  7. on script return → wf:completed (result, costTotal = sum of child costTotals)
  8. on throw/abort → wf:aborted (reason)
  9. on budget exceeded → wf:aborted ("token budget exceeded")
```

**Resume mechanics (edit-and-resume):** `resumeFromRunId` loads the prior `WorkflowJournal`, builds the `callIndex → {prompt, opts, result}` cache. As the (possibly edited) script executes, each `agent()` call computes its current `callIndex` + `prompt` + `opts`. If the cache has a matching entry (same index, same prompt, same opts) → return the cached `result` (no spawn, no token spend). If the prompt/opts changed, or the index is new → spawn. Entries past the last reused index are ignored (the script may be shorter). This is the "reuse the unchanged prefix, re-run the edited suffix" contract.

**Restart-recovery (reconcile):** `src/runtime/reconcile.ts` gains a workflow scan: on `session_start`, scan `.pi/fleet/workflows/` for non-terminal journals (`wf:started` without `wf:completed`/`wf:aborted`). An interrupted workflow becomes a resume candidate (visible in the Workflows view with a Resume action). The runner's resume path is the same `resumeFromRunId` mechanism — restart-recovery is just "resume with the unedited script." No partial-worktree concern (workflow scripts are JS, not edits — the *child agents* may have made edits, but each child's isolation/worktree is governed by its own `isolation` opt-in and the v0.11.1 seam).

### 3.6 The model surface (folded into the fleet tool — Q7=A)

No new tool. The existing fleet tool (currently `subagent` + `fleet_results`) gains a `workflow` surface. Two action groups:

**`workflow` action (run a workflow):**

| Param | Type | Default | Notes |
|---|---|---|---|
| `script` | string | required | the JS workflow script (NL-generated or user-authored) |
| `name` | string | none | save-as name (optional; saves the script as `<name>.js`) |
| `args` | unknown | none | passed to the script as `args` |
| `background` | boolean | `true` | non-blocking; live panel + auto-delivery (matches QuintinShaw) |
| `resumeFromRunId` | string | none | edit-and-resume: replay the unchanged prefix, re-run the edited suffix |
| `maxAgents` | number | 1000 | hard cap on total `agent()` calls (matches QuintinShaw) |
| `concurrency` | number | 3 (clamped to 16) | parallel `agent()` concurrency |
| `agentRetries` | number | 0 | default per-agent `retries` |
| `agentTimeoutMs` | number | unbounded | default per-agent `timeoutMs` |
| `tokenBudget` | number | unlimited | run-level `budget.total` |

**`workflow_control` action (list/status/pause/resume/stop):** the model (or the panel) controls a running workflow by canonical `runId`. `list` returns runs + states; `status` returns the run state + current phase + agent counts + token total; `pause`/`resume`/`stop` are the controls. Mirrors QuintinShaw's `workflow_control`.

**Keyword triggering (Q2=C):** the model generates a workflow script straight-to-script when a request is decomposable + the user authorizes it (the bounded word "workflow"/"workflows" arms the surface, like QuintinShaw 3.0 — the trigger *authorizes* the tool, doesn't *force* it; a question about workflows is answered plainly). Identifier-like text (`myworkflow`, `workflow_name`, `src/workflow-editor.ts`) does not trigger. Configurable/deferrable — the trigger is a thin layer over the `workflow` action; it can ship off-by-default and the model still uses `workflow({ script })` directly.

## 5. Edge cases

| Case | Behavior |
|---|---|
| `agent({ isolation: "worktree" })` in a non-git cwd | **synchronous fail-fast — NOT retryable** (v0.11.1 seam): `runBackgroundIsolated` pre-flight returns `{status:"failed",error}` → the runner maps the agent call to an immediate step failure. This is a *deterministic environment error* (non-git cwd), not a recoverable spawn failure — retrying would fail-fast identically (same cwd), so it does **not** consume a `retry`. The `agent()` call returns `null` (per the crash contract); the workflow script decides whether to catch it or let it abort. `retries` is reserved for *recoverable* failures (model hiccups, schema mismatch). |
| `agent({ schema })` mismatch | re-spawn (one repair attempt per `retry`); on `retries` exhaustion → the call fails → `wf:aborted` (no bespoke repair loop — Q6=A deferral) |
| `agent({ lifecycle: "default" })` | runs the full superpowers pipeline as one workflow step; 6-2 gates run inside each phase; the step resolves to the lifecycle's synthesized result; the lifecycle's `todoId` links to the workflow's `todoId` (cost rolls up) |
| `agent({ lifecycle })` + `isolation: "worktree"` | the lifecycle runs in the worktree (the v0.11.1 seam threads `worktreePath` into `runLifecycle`); the worktree is removed on lifecycle completion |
| `parallel()` with N thunks | concurrency clamped to `concurrency`; order preserved in result array; each thunk's `agent()` is a separate journal entry by execution index |
| `pipeline()` with 0 items | returns `[]` (no agent calls) |
| `workflow(child, args)` recursion | child gets its own `runId` linked to parent; shares parent's `budget` pool; **recursion depth cap of 3** (default; configurable via `WorkflowRunOpts.maxRecursionDepth`) prevents infinite `workflow()`-calls-`workflow()` loops — breaching the cap → `wf:aborted` ("workflow recursion depth exceeded") |
| `checkpoint()` in headless (model-driven) mode | `headless:"default"` (default) returns `opts.default` (default `true`); `headless:"abort"` aborts the workflow; the response is journaled so resume doesn't re-prompt |
| `checkpoint()` in interactive (panel) mode | surfaces in the Workflows view; the workflow pauses until the human responds; on session restart, an unanswered checkpoint → the workflow is a resume candidate (the checkpoint re-prompts on resume, unless its hash matches — see Note) |
| Budget exceeded mid-workflow | `wf:aborted` ("token budget exceeded"); the runner checks `budget.remaining()` before each `agent()` spawn |
| `maxAgents` exceeded | `wf:aborted` ("max agents (N) exceeded"); hard cap on total `agent()` calls |
| Script throws (non-deterministic error) | `wf:aborted` (reason = error message); the script's `vm` execution is wrapped in try/catch |
| Script uses a stripped global (`Date.now`) | `ReferenceError: Date is not defined` → `wf:aborted` (determinism contract enforced) |
| Resume with a shorter script | cache entries past the last reused index are ignored; the workflow completes with the shorter run |
| Resume with a reordered `agent()` | indices shift → all calls from the first reorder point mismatch → re-run (no crash; the cache is simply not reused) |
| Resume with an unchanged prefix + edited suffix | unchanged calls replay from cache (no spawn, no token spend); edited call + everything after re-runs |
| Interrupted workflow on restart | reconcile scans `.pi/fleet/workflows/` → resume candidate → Resume action replays the unedited script (full cache reuse) |
| `verify`/`judgePanel` reviewer spawn fails | the helper returns a structured failure (e.g. `verify` → `{real:false, realCount:0, total:0, votes:[]}`); the workflow script decides what to do (no auto-abort — helpers are call-site, the author composes them) |
| `loopUntilDry` hits `maxRounds` | returns the accumulated de-duped set (no abort — it's a discovery loop, "dry" is the stop condition) |
| Child agent crashes | the child's `RunRecord` is `failed`; the `agent()` call returns `null` (per QuintinShaw's `agent() => Promise<string \| structured value \| null>`); the script handles `null` |
| Concurrency contention | the `ConcurrencyPool` (SPEC-5a) gates `parallel()` concurrency; a busy pool queues thunks (no deadlock — the pool drains) |
| `phase()` re-declared mid-script | advances the current phase; subsequent `agent()` calls tag with the new phase |
| `workflow("name")` where name doesn't exist | `ReferenceError`-style → `wf:aborted` ("workflow '<name>' not found; available: …") |

**Note on `checkpoint` resume-identity:** the `checkpoint()` response is journaled by call index. On resume, if the prompt + `opts` (kind/choices/default/headless/timeoutMs) match the cached entry, the cached response is reused (no re-prompt). If any of those changed, the checkpoint re-prompts once (matching QuintinShaw 3.2's hash-widening behavior). This is a one-time effect per changed checkpoint.
